## 0. 用户反馈与一句话诊断

| # | 反馈（原意） | 诊断 |
|---|---|---|
| 1 | 比较式 CR：只找 A/B 差异，两边共有的问题被当「既定模式」放过 | 评审输入只有 A vs B，没有「需求/验收清单」，也没有「共有模式」这个必答项 |
| 2 | 自审偏差：基线、契约测试、规范是自己写的，CR 把基线当地面真值 | 基线（契约、测试、文档）没有受审环节；CR 的默认对象是「赛道偏离基线的程度」 |
| 3 | 依赖赛道自述：报告说「docs 不写 7」「按挂单日」「刻意不加 cache」就信了 | 没有证据优先规则，赛道产出也不要求逐条带证据；意图声明可以绕过需求 |
| 4 | 目标错位：在「让 gate 过」而不是「让需求被真正满足」 | 「通过」没有定义；测试全绿、契约不变被当成通过 |

一句话：现在的 CR 是「以基线为尺子、以差异为线索、以自述为证词」的评审；要换成「以需求为尺子、以清单为线索、以证据为证词」，并把基线本身列为被告。

## 1. 目标与非目标

**目标**

1. CR 先回答「需求是否被真正满足」，再回答「哪条赛道更好」；基线（契约/测试/文档/规范）在 CR 里是**被审对象**，不是尺子。
2. 「两边一样」从「既定模式」改为**基线证据**：共有模式必须列出来并逐条处置，默认怀疑基线。
3. 赛道自述逐条核对证据；意图声明不算证据。
4. 「通过」有可判定定义：验收清单逐条有证据 + 基线无未决问题 + 无阻塞实现问题；测试绿只是最低约束。
5. 把规则写进 **bootstrap 生成模板、本项目流程、格式规范、README/架构文档**，并用测试钉住 brief 与图标签的语义。

**非目标**

- 不加新节点：现有 common / gate / verdict / confirm 承载；
- 不改 lib/flow.js 解析器、不加诊断码；
- 不改赛道独立性、复盘轮次与胜负规则（改动少者胜出仍只在全部通过时适用）；
- 不强制 CR 报告落盘（保持会话内可追溯；需要留痕由用户决定）。

## 2. 现状与证据

### 2.1 比较式 CR（P1）

现状（docs/workflow-format.md §8.2 第 1–3 步；docs/racing-code.md ### cr 第 1–3 步）：

- 初审只有「逐 lane 读 diff、关键文件、在该 worktree 跑测试」；
- 「共同问题」的定义是「≥2 条 lane 的同一类问题」（workflow-format.md:368）。它要求 CR 先注意到「同一类」，但没有要求**主动枚举两边相同或同样缺失的模式**；
- 评审动作围绕「每条 lane 自己的问题」展开，A/B 差异是默认视角；两边一致的行为没有进入任何清单。两边都「没写/没做」时没有失败信号，于是被当成既定模式；
- §8.3 的解释把共同问题说成「多半是约束缺口」（workflow-format.md:396-398），方向是对的，但入口仍靠「两条都犯了明显错误」。

### 2.2 自审偏差（P2）

- 本项目的 contract-tests 与 cr 都是 session（docs/racing-code.md:10-11）→ 基线作者与裁判是同一个会话、同一个模型；
- 模板与格式规范从未把基线列为评审对象：CR 的问题分类是「契约/测试缺口、实现缺陷、约束违背、风格」（docs/racing-code.md:125），主语都是「赛道」；对基线的追问只发生在「共同问题追一层约束」（第 4 步），即**只有赛道先犯错，基线才会被问**；
- baseline 关口（docs/racing-code.md:98-100）只有「提交基线/先完善契约」两个选项，交接材料没有要求列出**基线的未证明前提与测试盲区**；
- 换模型不是完整解法：基线是在会话里写的，裁判如果仍拿到同一份带「正确」光环的基线，仍会只审偏离；而把 CR 委派出去，关口材料还多一层转述。可行的是**显式的基线审计步骤 + 用户复核**。

### 2.3 依赖自述（P3）

- 初审「读 diff、关键文件、跑测试」（workflow-format.md:366；docs/racing-code.md:123-124）；
- 赛道产出只要求「diff 摘要 + 测试输出 + 你认为没做好的地方」（docs/racing-code.md:114；bootstrap 的 laneBrief 只有 2 条，lib/bootstrap.js:151-157）；
- 没有任何规则要求「报告里的每条结论必须能被文件/测试/命令复现」；「刻意不加 cache」这类意图声明可以绕过需求。

### 2.4 目标错位（P4）

- 「通过」没有定义，实际被理解为「没有阻塞问题」（workflow-format.md §8.2 第 7 步、§8.4），而「阻塞问题」由 CR 自己裁量；
- 判据里最硬的是「测试全绿」（契约测试在 baseline 已定稿），于是「不改契约、不改测试、让测试绿」成了事实上的优化目标；
- §8.4 的定胜负是「更高分者 / 改动少者」，但没有把「验收清单逐条满足」写进通过条件；「测试绿 ≠ 需求满足」这一点从未被写出来。

### 2.5 现场样本（不是为了指责赛道，而是说明判据只到测试层）

上一轮 manual-cr-notes 的两条赛道各自只提交了 1 行文案（0.0.x-racing/implement-a @ 90b115c 与 implement-b @ 9c933d5），差异只是措辞；契约测试断言的是 3 个关键词（test/bootstrap.test.mjs:170-179）。两条赛道都能过，并不说明模板改好了。**本计划执行时也要以此自省：不要用「测试绿」证明 CR 协议改好了。**

**收口上一轮时的第二个现场样本**：该轮的 plan 写「增加第 4 条（仍满足 2–4 条可执行规则）」，但 `BRIEFS.cr` 原本已有 4 条（含 in-session 行），两条赛道都加成了 5 条；`lib/bootstrap.js:124` 与 `docs/bootstrap.md:186` 的「2–4 行」规则被同时违反，而契约测试只钉关键词、没有钉行数。两条赛道一样错——这正是「共有模式 = 基线缺陷」的实例，也说明模板的行数预算必须进测试。

## 3. 设计

### 3.1 CR 五步法（顺序不能换）

写进 docs/racing-code.md ### cr 的正文如下（格式规范 §8.2 同步为同一语义）：

```markdown
CR 要回答三件事：需求被真正满足了吗？基线本身对吗？赛道自己的证据成立吗？

0. 冻结标准（读任何 lane diff 之前）：从 plan 文档的「需求 + 验收标准」、用户需求原文和本轮契约里，先写出两张表：
   - 验收清单：每条都能被证据判定，覆盖正常路径 / 边界 / 失败路径；验收标准缺失或不可判定 → 停下问用户，不得自己发明标准；
   - 基线断言清单：契约、测试、文档里哪些前提还没被证明（「docs 不写 7」「按挂单日」「不加 cache 是刻意的」都是断言，不是事实）。
   清单一旦冻结，本轮不因赛道表现而改；要改就记为基线问题，走 gate。
1. 审基线（把基线当被告，而不是尺子）：逐条核对基线断言——与需求原文、上游文档、已有行为是否一致，证据是什么。
   基线是本会话上一轮写的，不因为作者是「我」就免检；契约与测试是工具，不是需求本身；规范也可能写错。
   每条结论只有三类：成立 / 基线缺陷 / 说不清；后两类都是基线问题（不是某条赛道的错），走 gate。
   「回 plan 改基线」是 CR 的正确产出，不是 CR 失败；为了让 gate 过而维持错误基线才是失败。
2. 列共有模式（比较式 CR 的反面）：显式列出两条赛道相同或同样缺失的行为——都缺 cache、都用 union/判空绕路、
   文档都没写某条规则、都只做到测试下限……每条给且只给三种处置：
   - 有证据证明正确：写清为什么（引用需求/文档/行为证据，不能写「两边都这样」）；
   - 基线缺陷：走 gate；
   - 用户接受：记入已接受清单，写明接受理由（「两边一样」不是理由）。
   「两边一样」只说明两条赛道读到同一份基线，不是正确性证据；拿不准 → 默认按基线缺陷走 gate。
   两条赛道对同一需求做了相反决定，多半是基线歧义，同样按共同问题处理。
3. 核对赛道自述（证据优先）：赛道报告里的每条结论逐条核对，标为 已验证（文件:行 / 测试名 / 命令输出）、
   不成立（反证：…）或 无法验证（没有证据）。意图声明不算证据：需求/约束里没写豁免，「刻意不加 cache」不能抵消缺陷；
   无法验证的结论不能作为「通过」依据，写进报告的「未验证清单」。
4. 逐赛道对照验收清单：不做 A 对 B 的笼统比较——对验收清单逐条给 A/B 各自的结论与证据（用「验收项 × 赛道」矩阵，
   把两边都不过的格子显性化）。A/B 差异只在两处使用：① 发现基线歧义（同一需求相反决定 → 按共同问题处理）；
   ② 全部通过后按改动量定胜负（第 11 条）。
```

原有第 5–12 条的语义保持不变（编号顺延为 5–14），只做三处调整：

| 步骤 | 调整 |
|---|---|
| 原第 5 步（问题归类） | 每条问题必须带证据与严重度（阻塞/非阻塞） |
| 原第 6 步（gate） | 材料必须含第 0–4 步的验收矩阵、基线审计、共有模式、自述核对；选「接受现状」逐条写接受理由 |
| 原第 10 步（verdict） | 材料必须含完整清单与矩阵；「通过」按 §3.2 的定义逐条写 |

### 3.2 通过判定与反目标

一条赛道「通过」= 验收清单逐条满足且有证据 + 基线审计没有未决的基线问题 + 没有阻塞的实现/约束问题。

**测试全绿、契约没改、测试没改都不是「通过」**——它们只是最低约束。为了「让 gate 过」而收窄问题、放过共有模式、或把测试绿当需求满足，属于 CR 失职。发现基线问题并回 gate/plan 是 CR 的正确产出，不是失败。

### 3.3 CR 报告结构（gate/verdict 必须带这些材料）

- 验收清单（冻结版）+ 验收项 × 赛道矩阵（每格：满足/不满足 + 证据）；
- 基线审计表：断言 | 来源 | 证据 | 结论（成立/基线缺陷/说不清）；
- 共有模式清单：模式 | A/B 表现 | 处置（有证据正确/基线缺陷/用户接受）| 依据；
- 自述核对表：结论 | 证据 | 已验证/不成立/无法验证；
- 每赛道问题清单（逐条全文，带证据与阻塞/非阻塞）；
- 共同/基线问题（→ gate）；用户的人工 CR 意见（逐条，与自动问题分开）；
- 通过判定（逐条）+ 胜者建议（打分依据）；未验证清单（不能作为通过依据）。

**回答「无共同问题」时**：共有模式清单必须为空，或每条都有「有证据的正确 / 用户接受」处置；否则不允许走 verdict。

### 3.4 图上的措辞（不改结构）

| 现状 | 改为 | 理由 |
|---|---|---|
| common{"存在共同问题?"} | common{"存在共同问题或基线缺陷?"} | 让「基线错了」成为图上可见的一种「有」；出边文字不变（有/无） |
| verdict{"每条赛道都通过?"} | verdict{"每条赛道都满足验收清单?"} | 把「通过」锚到验收清单，而不是测试绿 |
| gate 选项「完善约束」 | 保持 | 基线缺陷也按「完善约束」回 plan，在 ### cr 里写清 |

不改图结构的理由：现有 common → gate → plan 已经能承载「基线缺陷回 plan」；加节点会让每个项目多一次往返，并要改格式语义、诊断与所有示例。

## 4. 备选方案与被否原因

| 方案 | 结论 | 原因 |
|---|---|---|
| 只换 CR 模型（避开基线作者） | 不做结构性要求 | 基线仍在同一份上下文里被当作标准；委派 CR 还让关口材料多一层转述。协议补偿 + 用户复核更直接；是否给 CR 指定独立模型留给用户按项目选（见 §10 决策 5） |
| 新增 baseline-audit 阶段或用户关口节点 | 否 | 多一次往返；现有 common → gate → plan 已覆盖；所有示例与格式语义都要改 |
| 插件硬编码检查「CR 是否审了基线」 | 否 | 无法从文本可靠判断；也违反「代码不硬编码阶段名/语义」的约束 |
| 流程文件里声明结构化 CR checklist | 留到 v2 | 可测性更好，但引入新格式、诊断与渲染；本轮先用固定报告结构 + 测试钉 brief 语义 |
| CR 报告强制落盘 docs/cr/ | 否 | 既有决策是插件不主动写文件、留痕由用户决定；需要时用户再落盘 |

## 8. 验收标准

- npm test 全绿（含 §5 新用例）；
- flow_stages 返回的 cr 说明含五步法与通过判定；common / verdict 标签更新；
- 生成模板 full 与 minimal 的 cr brief 都含：验收清单、基线、共有模式、证据、测试绿≠需求满足、人工意见；
- lane brief 含逐条证据要求；
- cr brief 行数 ≤4（含 in-session 行），由测试钉住；
- 文档链接 0 missing，图例在 racing-code / workflow-format / bootstrap / architecture / 两份 README 同步；
